Context Compaction

How Mistral Vibe keeps long conversations inside the model's context window by replacing old history with a summary.

1. Why compaction exists

Every turn, the agent sends the whole conversation to the model: system prompt, user messages, assistant replies and tool results. Tool results can be large (file contents, command output), so the history grows quickly. Once it reaches the model's context limit, requests fail.

Compaction fixes this. The agent asks a model to write a handoff summary of the work so far. It then appends one message containing that summary, and from then on the model only sees the system prompt plus that message and everything after it.

2. When it runs

Automatic trigger

AutoCompactMiddleware.before_turn (vibe/core/middleware.py) runs before every turn. It compares the last known stats.context_tokens with the active model's auto_compact_threshold:

if threshold > 0 and context.stats.context_tokens >= threshold:
    return MiddlewareResult(action=MiddlewareAction.COMPACT)

The agent loop handles that action in _run_compaction (vibe/core/agent_loop/_loop.py). It emits a CompactStartEvent, calls compact(), sends an auto_compact_triggered telemetry event with the status (success, failure or cancelled) and reports the result.

How the threshold is chosen

Model declaresThreshold used
Its own auto_compact_thresholdThat value
A context window only80% of the window (AUTO_COMPACT_WINDOW_RATIO = 0.8). Compaction is itself a model call that carries the conversation, so triggering at the true ceiling would fail exactly when it is needed.
NeitherThe global auto_compact_threshold setting (default 200_000 tokens)
Threshold set to 0Auto-compaction is disabled

Early warning

ContextWarningMiddleware injects a one-time message when usage reaches 50% of the threshold: "You have used N% of your context budget (x/y tokens before older messages are summarized)". The percentage is relative to the compaction point, not the model's full window, so a user who deliberately capped the conversation is not told they have capacity they gave up.

3. The compaction pipeline

messages→ select_model_context→ collect_prior_user_messages→ model call → <summary>→ render envelope→ append boundary + save
  1. Snapshot the visible context select_model_context finds the latest compaction boundary and returns the system messages plus everything from that boundary onward. On a first compaction there is no boundary, so it returns everything.
  2. Pick user messages to keep collect_prior_user_messages walks the user messages newest-first within a budget of COMPACT_USER_MESSAGE_MAX_TOKENS (20,000). The message that overflows the budget is middle-truncated. System-injected messages and old summaries are skipped. Messages kept by an earlier compaction are parsed back out of the old envelope and merged with newer real user turns, so they survive repeated compactions.
  3. Ask a model for a summary The compaction prompt (vibe/core/prompts/compact.md) asks for a handoff summary: the user's goal and constraints, key decisions, files touched with one-line status, the concrete next step, and any identifiers needed. The model must wrap its answer in <summary>…</summary>, which extract_summary pulls out. Extra user instructions can be appended under "Additional Instructions".
  4. Build the envelope render_compaction_context combines the kept user messages and the summary into a single message (see below).
  5. Append and save The envelope is appended as an injected user message tagged context_boundary="compaction". context_tokens is reset to 0 because the true size is unknown without an API call; the next LLM turn recomputes it from real usage. Then the session is saved.
Atomicity. Summarization runs on a local copy of the messages. The live MessageList is only changed in the last step, by appending the boundary. A failure therefore never leaves a half-trimmed conversation.

Prompt-cache friendly by design

The first (primary) call appends the summary request to the live conversation, so the provider can reuse its cached prefix and the call is cheap. It uses the same tools and tool choice as the session, which keeps that prefix identical.

4. The envelope message

You are continuing a trajectory after a context compaction.

Here are some of the most recent previous user messages, preserved
verbatim where possible. Treat them as prior context, not as new requests.

<previous_user_messages>
<previous_user_message>
...first kept message...
</previous_user_message>
<previous_user_message>
...second kept message...
</previous_user_message>
</previous_user_messages>

Here is a summary of what has happened so far:

<compaction_summary>
...the model's summary...
</compaction_summary>

Reserved tags that appear inside a user's own text are HTML-escaped (_escape_reserved_previous_user_message_tags), so user content cannot forge or break the envelope. parse_previous_user_messages reverses the format when the next compaction needs the old messages.

5. What the model sees afterwards

Before compaction                    After compaction
─────────────────                    ─────────────────
system prompt                        system prompt
user 1                               [ENVELOPE: kept user msgs + summary]
assistant 1 + tool results           user 12
user 2                               assistant 12 …
…                                    (new turns continue here)
user 11
assistant 11

The old messages are not deleted from the stored session. They stay in the history, but select_model_context hides everything before the latest boundary when building a request.

6. Failure handling

SituationWhat happens
The summary request itself is too long for the model (ContextTooLongError)drop_oldest_round removes the oldest round (user message, assistant replies, tool results) and retries, up to 3 times. It stops early if only the latest round remains.
The primary call returns tool calls (tool_call) or has no <summary> block (empty_summary)Unless raise_on_compaction_failure is set, a fallback runs: a dedicated system prompt, thinking turned off, no tools, and the conversation rendered as a text transcript. This deliberately breaks the prompt cache, because a reliable summary is worth more.
The fallback also failsA compaction_failed telemetry event is sent with the primary failure reason. The placeholder (no summary available) is used so the session can continue.
raise_on_compaction_failure = trueNo fallback. CompactionFailedError is raised with the reason.

The fallback transcript (_render_transcript) keeps user text, assistant text and tool calls such as [calls read_file({...})], so the summarizer sees what produced each tool result. It drops system messages and reasoning content: reasoning is ephemeral and would bloat the very transcript compaction is trying to shrink.

7. Helper functions

FunctionPurpose
extract_summaryReturns the text inside <summary> or None if absent or empty.
select_model_contextKeeps system messages plus everything from the latest compaction boundary.
collect_prior_user_messagesChooses which user messages survive, within the token budget.
drop_oldest_roundRemoves the oldest user round to recover from an overlong summary request.
render_compaction_contextBuilds the envelope text.
parse_previous_user_messagesReads kept user messages back out of an envelope.
reorder_for_tool_adjacencyProviders such as Anthropic require each assistant tool_use to be followed immediately by its tool_result. A message steered into a running turn can land in that gap; this moves it to just after the results. It is pure and order-stable, so it is safe to run on every outbound request.
render_teleport_summary_requestBuilds a summary request used when teleporting a session to Vibe Code Web, with a character limit.

8. Configuration
